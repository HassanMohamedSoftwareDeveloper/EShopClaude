# Ordering.Api 01 — Persistence

**Status:** Not started

## Goal

Give Ordering.Api its own schema in `orderingdb`, with orders and their lines. After this spec the service connects to Postgres through Aspire, waits for the database, and creates the `Orders` and `OrderLines` tables on startup. Every order endpoint builds on this.

## Context

- **Starting point on `main`** (after PLAN 2.1 and catalog-01..04):
  - AppHost declares `postgres` (with pgAdmin), `catalogdb`, `orderingdb` and `redis`. `orderingapi` has only `.WithHttpHealthCheck("/health")` and does not reference `orderingdb` yet.
  - Ordering.Api already has the `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` 13.6.4 package, but no code uses it.
  - `Program.cs` has the root `MapGet("/")` and an empty `/api` group.
  - Catalog.Api (`src/EShopClaude.Catalog.Api/Program.cs`, `Data/CatalogDbContext.cs`) is the reference implementation of this exact pattern. Mirror it.
- **Connection string**: `WithReference(orderingDb)` in the AppHost injects the env var `ConnectionStrings__orderingdb`, and the Aspire client integration reads it as `ConnectionStrings:orderingdb`.
  - The AppHost is the only source. No appsettings file holds a connection string.
  - A standalone run (port 5103, no AppHost) therefore fails at startup with Aspire's missing-connection-string error. This is intended.
- **Startup order**: `WaitFor(orderingDb)` keeps `orderingapi` in Waiting until `orderingdb` is healthy. `webfrontend` already waits for `orderingapi`, so it now waits for the database too.
- **Schema creation**:
  - In `Program.cs`, after the app is built and before it starts serving, a DI scope resolves `OrderingDbContext` and awaits `Database.EnsureCreatedAsync()`.
  - No request is served before both tables exist.
  - A database failure crashes startup, and the dashboard shows `orderingapi` as failed.
  - `EnsureCreated` makes no change when the tables already exist, so restarting only `orderingapi` is safe.
- **Integration defaults stay on**: EF Core retry on transient failures, Npgsql tracing and metrics, and the DbContext health check on `/health`. Nothing is configured beyond the defaults.
- **Naming**: tables and columns use EF's default PascalCase names (`"Orders"`, `"OrderLines"`, `"Id"`, …), which are quoted in Postgres. EF's default names for the FK (`FK_OrderLines_Orders_OrderId`) and its index (`IX_OrderLines_OrderId`). No naming-convention package.
- **Relationship**: one-way. `Order.Lines` is the only navigation, and `OrderLine` carries the `OrderId` FK property with no `Order` back-reference.
- **`CreatedAt`**: column only, with no DB default. ordering-02 sets `DateTimeOffset.UtcNow` when it creates an order.

## Depends on

Nothing. PLAN 1.x and 2.1 (skeleton, infra resources) are already merged.

## Scope

- [ ] AppHost: `orderingapi` `.WithReference(orderingDb).WaitFor(orderingDb)`.
- [ ] `Order` entity: Id (int identity), BuyerId, CustomerName, CustomerEmail, CreatedAt (`DateTimeOffset` UTC), Total (`decimal`), Lines.
- [ ] `OrderLine` entity: Id, OrderId FK, ProductId, ProductName, UnitPrice (`decimal`), Quantity.
- [ ] `OrderingDbContext` with cascade delete from Order to Lines.
- [ ] `AddNpgsqlDbContext<OrderingDbContext>("orderingdb")`.
- [ ] Startup: `Database.EnsureCreated()`.
- Why AppHost wiring and DbContext registration share one spec: `AddNpgsqlDbContext` throws when the `orderingdb` connection string is missing, so neither part can be checked alone.

## Data model

Table `"Orders"` in `orderingdb`, mapped from entity `Order` through `DbSet<Order> Orders`:

| Column | CLR type | Postgres type | Constraints |
|---|---|---|---|
| Id | `int` | `integer` | PK, `GENERATED BY DEFAULT AS IDENTITY` |
| BuyerId | `string` | `varchar(100)` | NOT NULL |
| CustomerName | `string` | `varchar(100)` | NOT NULL |
| CustomerEmail | `string` | `varchar(254)` | NOT NULL |
| CreatedAt | `DateTimeOffset` | `timestamp with time zone` | NOT NULL, no default |
| Total | `decimal` | `numeric(18,2)` | NOT NULL |

Navigation `Lines`: `List<OrderLine>`, initialised to `[]`. It is not a column.

Table `"OrderLines"` in `orderingdb`, mapped from entity `OrderLine` through `DbSet<OrderLine> OrderLines`:

| Column | CLR type | Postgres type | Constraints |
|---|---|---|---|
| Id | `int` | `integer` | PK, `GENERATED BY DEFAULT AS IDENTITY` |
| OrderId | `int` | `integer` | NOT NULL, FK → `"Orders"."Id"` `ON DELETE CASCADE`, index `IX_OrderLines_OrderId` |
| ProductId | `int` | `integer` | NOT NULL, no FK (Catalog's id; separate database) |
| ProductName | `string` | `varchar(100)` | NOT NULL (same length as Catalog `Product.Name`) |
| UnitPrice | `decimal` | `numeric(18,2)` | NOT NULL (same precision as Catalog `Product.Price`) |
| Quantity | `int` | `integer` | NOT NULL |

- No other columns, indexes, check constraints or relations. In particular there is no index on `BuyerId` and no status column.
- Constraints (keys, required, max lengths, precision, the relationship and its cascade) are set in the model configuration of `OrderingDbContext` (fluent API), not with attributes on the entities.
- The relationship is configured explicitly: `HasMany(o => o.Lines).WithOne().HasForeignKey(l => l.OrderId).OnDelete(DeleteBehavior.Cascade)`.
- Ids come from Postgres. The database is ephemeral, so every run starts with 0 rows in both tables.

## Definition of Done

Each line is a check you can run, with its expected result. Shell commands use Git Bash syntax.

1. **Build**: `dotnet build src/EShopClaude.sln` → `0 Error(s)`, and the same warning count as the same command on `main`.
2. **Run**: `cd src && aspire run` → Dashboard → Resources: every resource shows State **Running** and Health **Healthy**.
3. **Wiring**: Dashboard → `orderingapi` → Details → Relationships → `orderingdb` is listed as both Reference and WaitFor.
4. **Connection string**: Dashboard → `orderingapi` → Details → Environment variables → `ConnectionStrings__orderingdb` is present and contains `Database=orderingdb`.
5. **Schema, `Orders`**: find the container with `docker ps --filter name=postgres`. Aspire's Postgres requires a password even on the local socket, so take it from the container's own `POSTGRES_PASSWORD` env var: `docker exec <container> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U postgres -d orderingdb -c "\d \"Orders\""'`. Expect exactly six columns:
   - `Id | integer | not null | generated by default as identity`
   - `BuyerId | character varying(100) | not null`
   - `CustomerName | character varying(100) | not null`
   - `CustomerEmail | character varying(254) | not null`
   - `CreatedAt | timestamp with time zone | not null` (Default column empty)
   - `Total | numeric(18,2) | not null`

   Also expect the index `"PK_Orders" PRIMARY KEY, btree ("Id")` and, under "Referenced by", `TABLE ""OrderLines"" CONSTRAINT "FK_OrderLines_Orders_OrderId" FOREIGN KEY ("OrderId") REFERENCES "Orders"("Id") ON DELETE CASCADE`.
6. **Schema, `OrderLines`**: same command with `\d \"OrderLines\"`. Expect exactly six columns:
   - `Id | integer | not null | generated by default as identity`
   - `OrderId | integer | not null`
   - `ProductId | integer | not null`
   - `ProductName | character varying(100) | not null`
   - `UnitPrice | numeric(18,2) | not null`
   - `Quantity | integer | not null`

   Also expect the indexes `"PK_OrderLines" PRIMARY KEY, btree ("Id")` and `"IX_OrderLines_OrderId" btree ("OrderId")`, and exactly one foreign-key constraint, `"FK_OrderLines_Orders_OrderId" FOREIGN KEY ("OrderId") REFERENCES "Orders"("Id") ON DELETE CASCADE`. pgAdmin (opened from the dashboard) shows both tables under `orderingdb` → Schemas → public → Tables.
7. **No data**: `docker exec <container> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U postgres -d orderingdb -tAc "SELECT (SELECT count(*) FROM \"Orders\") || \",\" || (SELECT count(*) FROM \"OrderLines\")"'` → `0,0`.
8. **Cascade delete works**: pipe this SQL into the container:

   ```sh
   docker exec -i <container> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U postgres -d orderingdb -tA' <<'SQL'
   WITH o AS (
     INSERT INTO "Orders" ("BuyerId","CustomerName","CustomerEmail","CreatedAt","Total")
     VALUES ('dod','DoD','dod@example.com',now(),2.00) RETURNING "Id")
   INSERT INTO "OrderLines" ("OrderId","ProductId","ProductName","UnitPrice","Quantity")
   SELECT "Id",1,'DoD',1.00,2 FROM o;
   DELETE FROM "Orders" WHERE "BuyerId" = 'dod';
   SELECT count(*) FROM "OrderLines";
   SQL
   ```

   → `INSERT 0 1`, `DELETE 1`, then `0`. Check 7 returns `0,0` again afterwards.
9. **Logs**: Dashboard → Structured logs, resource `orderingapi`, filter `CREATE TABLE` → exactly two entries, category `Microsoft.EntityFrameworkCore.Database.Command`, one containing `CREATE TABLE "Orders"` and one containing `CREATE TABLE "OrderLines"`.
10. **Health**: `GET <orderingapi endpoint from dashboard>/health` → `200` with body `Healthy`.
11. **Restart is safe**: Dashboard → `orderingapi` → Restart. Expect:
    - it returns to Running/Healthy;
    - Console logs show no exception;
    - check 7 still returns `0,0`;
    - check 9 still shows exactly two `CREATE TABLE` entries.
12. **Fail fast standalone**: with the AppHost stopped, `dotnet run --project src/EShopClaude.Ordering.Api` exits at startup with an `InvalidOperationException` whose message names `ConnectionStrings:orderingdb`.
13. **Diff scope**: `git diff --stat main` lists only the files in Files touched.
14. **Non-goals held**: both commands → no matches:
    - `git grep -nE "Migrations|WithDataVolume|HasData|HasDefaultValueSql|Map(Get|Post|Put|Delete)\(\"/orders" -- src`
    - `git grep -nwE "Status|Order Order" -- src/EShopClaude.Ordering.Api`
