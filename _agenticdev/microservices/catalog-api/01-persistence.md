# Catalog.Api 01 — Persistence

**Status:** Not started

## Goal

Give Catalog.Api its own database schema in `catalogdb`. After this spec the service connects to Postgres through Aspire, waits for the database before it starts, and creates the `Products` table on startup. The seed and the endpoints build on this.

## Context

- **Starting point on `main`** (after PLAN 2.1):
  - AppHost declares `postgres` (with pgAdmin), `catalogdb`, `orderingdb` and `redis`, but `catalogapi` does not reference `catalogdb` yet.
  - Catalog.Api already has the `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` 13.6.4 package, but no code uses it.
  - `Program.cs` has an empty `/api` group.
- **Connection string**: `WithReference(catalogDb)` in the AppHost injects the env var `ConnectionStrings__catalogdb`, and the Aspire client integration reads it as `ConnectionStrings:catalogdb`.
  - The AppHost is the only source. No appsettings file holds a connection string.
  - A standalone run (port 5101, no AppHost) therefore fails at startup with Aspire's missing-connection-string error. This is intended.
- **Startup order**: `WaitFor(catalogDb)` keeps `catalogapi` in Waiting until `catalogdb` is healthy.
- **Schema creation**:
  - In `Program.cs`, after the app is built and before it starts serving, a DI scope resolves `CatalogDbContext` and awaits `Database.EnsureCreatedAsync()`.
  - No request is served before the table exists.
  - A database failure crashes startup, and the dashboard shows `catalogapi` as failed.
  - `EnsureCreated` makes no change when the table already exists, so restarting only `catalogapi` is safe.
- **Integration defaults stay on**: EF Core retry on transient failures, Npgsql tracing and metrics, and the DbContext health check on `/health`. Nothing is configured beyond the defaults.
- **Naming**: tables and columns use EF's default PascalCase names (`"Products"`, `"Id"`, …), which are quoted in Postgres. No naming-convention package.

## Scope

- [ ] AppHost: `catalogapi` `.WithReference(catalogDb).WaitFor(catalogDb)`.
- [ ] `Product` entity: Id (int PK), Name, Description, Price (`decimal`).
- [ ] `CatalogDbContext` with `DbSet<Product> Products`.
- [ ] `AddNpgsqlDbContext<CatalogDbContext>("catalogdb")` in `Program.cs`.
- [ ] Startup: `Database.EnsureCreated()`.
- Why AppHost wiring and DbContext registration share one spec: `AddNpgsqlDbContext` throws when the `catalogdb` connection string is missing, so neither part can be checked alone.

## Data model

Table `"Products"` in `catalogdb`, mapped from entity `Product` through `DbSet<Product> Products`:

| Column | CLR type | Postgres type | Constraints |
|---|---|---|---|
| Id | `int` | `integer` | PK, `GENERATED BY DEFAULT AS IDENTITY` |
| Name | `string` | `varchar(100)` | NOT NULL |
| Description | `string` | `varchar(500)` | NOT NULL |
| Price | `decimal` | `numeric(18,2)` | NOT NULL |

- No other columns, indexes or relations.
- Constraints (key, required, max lengths, precision) are set in the model configuration of `CatalogDbContext` (fluent API), not with attributes on `Product`.
- Ids come from Postgres. On a fresh, ephemeral database the catalog-02 seed gets ids 1..n in insert order.

## Definition of Done

Each line is a check you can run, with its expected result.

1. **Build**: `dotnet build src/EShopClaude.sln` → `0 Error(s)`, and the same warning count as the same command on `main`.
2. **Run**: `cd src && aspire run` → Dashboard → Resources: every resource shows State **Running** and Health **Healthy**.
3. **Wiring**: Dashboard → `catalogapi` → Details → Relationships → `catalogdb` is listed as both Reference and WaitFor.
4. **Connection string**: Dashboard → `catalogapi` → Details → Environment variables → `ConnectionStrings__catalogdb` is present and contains `Database=catalogdb`.
5. **Schema**: find the container with `docker ps --filter name=postgres`. Aspire's Postgres requires a password even on the local socket, so take it from the container's own `POSTGRES_PASSWORD` env var: `docker exec <container> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U postgres -d catalogdb -c "\d \"Products\""'`. Expect exactly four columns:
   - `Id | integer | not null | generated by default as identity`
   - `Name | character varying(100) | not null`
   - `Description | character varying(500) | not null`
   - `Price | numeric(18,2) | not null`

   Also expect the index `"PK_Products" PRIMARY KEY, btree ("Id")`. pgAdmin (opened from the dashboard) shows the same table under `catalogdb` → Schemas → public → Tables.
6. **No data**: `docker exec <container> sh -c 'PGPASSWORD="$POSTGRES_PASSWORD" psql -U postgres -d catalogdb -tAc "SELECT count(*) FROM \"Products\""'` → `0`.
7. **Logs**: Dashboard → Structured logs, resource `catalogapi`, filter `CREATE TABLE` → exactly one entry, category `Microsoft.EntityFrameworkCore.Database.Command`, message containing `CREATE TABLE "Products"`.
8. **Health**: `GET <catalogapi endpoint from dashboard>/health` → `200` with body `Healthy`.
9. **Restart is safe**: Dashboard → `catalogapi` → Restart. Expect:
   - it returns to Running/Healthy;
   - Console logs show no exception;
   - check 6 still returns `0`;
   - check 7 still shows exactly one `CREATE TABLE` entry.
10. **Fail fast standalone**: with the AppHost stopped, `dotnet run --project src/EShopClaude.Catalog.Api` exits at startup with an `InvalidOperationException` whose message names `ConnectionStrings:catalogdb`.
11. **Diff scope**: `git diff --stat main` lists only the files in Files touched.
12. **Non-goals held**: `git grep -nE "Migrations|WithDataVolume|HasData|MapGet\(\"/api" -- src` → no matches.
